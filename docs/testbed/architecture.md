# 아키텍처

테스트베드 시스템의 전체 구조와 확정된 결정입니다. 이 문서의 결정은 **재검토·대안 제시 금지**입니다.

## 1. 용어

| 용어           | 뜻                                                                                                                                         |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 제품 (SUT)     | 개발·검증 대상. 예: API 게이트웨이, AI 게이트웨이                                                                                          |
| 테스트베드     | 제품을 검증하고 동작시키는 상대 시스템. 사람과 에이전트가 함께 씀                                                                          |
| `testbed-base` | 이 저장소. `hwahee/boilerplate`의 이력을 이어받은 중간 레포. 모든 테스트베드의 공통 런타임·대시보드 프레임·공통 위젯·기본 배치·문서를 가짐 |
| 공통 런타임    | `testbed-base`가 주는 코드: 코어 호스트, 이벤트 버스, Run 저장소, 제어 서비스, REST/MCP/WS 어댑터, 제어 락                                 |
| 하네스         | 에이전트가 문서를 읽고 테스트베드를 만들게 하는 작업 체계: 문서 구조, 스펙 템플릿, CLAUDE.md 규칙, 마일스톤, 검증 절차                     |
| 코어           | 테스트베드의 실제 기능(대역 서버, 부하 발생기, 시나리오 실행기). 기본은 Bun 프로세스 안, 필요하면 외부 프로세스                            |
| glue           | Bun 서버. 외부 코어를 띄우고 감시하며 대시보드·제어면과 이어 줌                                                                            |
| 데이터면       | 제품과 코어가 주고받는 트래픽(TCP, HTTP, 제품이 호출하는 MCP, LLM API 등)                                                                  |
| 제어면         | 테스트베드를 조작·관찰하는 통로: REST `/testbed/api`, MCP `/testbed/mcp`, WS `/testbed/ws`                                                 |
| Run            | 하나의 시험 단위. 시작부터 종료까지의 이벤트를 하나로 묶음                                                                                 |
| actor          | 행위 주체: `product` · `human` · `agent` · `ci` · `system`                                                                                 |
| 스펙           | 테스트베드 하나의 구현 세부사항 문서(`docs/spec.md`). 테스트베드마다 하나이고, 바뀌면 같은 문서를 갱신함                                   |

## 2. 레포 계보

```
hwahee/boilerplate (범용 풀스택)
        │ 이력 이어받기 + docs/upgrade-guides
        ▼
hwahee/testbed-base ── 공통 런타임, 대시보드 프레임·공통 위젯·기본 배치, docs/testbed/*, 스펙 템플릿, 시험용 코어(샘플·관찰)
        │ 이력 이어받기 + docs/upgrade-guides (testbed-base 자체 가이드)
        ├──▶ testbed-mcp-mock
        ├──▶ testbed-llm-mock
        └──▶ testbed-<이름> ...
```

- `testbed-base`는 보일러플레이트의 다운스트림이면서 각 테스트베드의 업스트림입니다.
- **이력 이어받기**: GitHub에서는 자기 레포를 같은 계정으로 fork할 수 없습니다. 그래서 빈 레포를 만들고 업스트림의 `main` 이력을 push합니다. 이후 업스트림 변경은 `upstream` 리모트를 두고 수동으로 머지합니다.

  ```sh
  git remote add upstream https://github.com/hwahee/boilerplate   # 테스트베드 레포라면 hwahee/testbed-base
  git fetch upstream
  git merge upstream/main
  ```

  머지한 뒤에는 [../upgrade-guides/](../upgrade-guides/README.md)에서 아직 적용하지 않은 가이드를 따릅니다. 충돌이 나면 가이드의 "충돌 해결 원칙"을 따릅니다(예: `testbed-base`가 지운 보일러플레이트 데모 파일은 삭제를 유지).

- 공통 런타임 코드는 `src/server/testbed/`, `src/client/testbed/`, `src/shared/testbed/`에 모읍니다. 테스트베드별 코드는 각 폴더의 `cores/<코어 id>/`에 둡니다. 업스트림 머지 때 충돌 면적을 줄이기 위함입니다.
- 테스트베드 레포에서는 공통 런타임(`src/*/testbed/` 중 `cores/` 밖)을 고치지 않습니다. 필요하면 `testbed-base`에 제안합니다.
- **시험용 코어**: 샘플 코어(TCP echo)와 관찰 코어는 공통 런타임의 시험 재료이며 `src/server/testbed/testing/sample-core/`·`observer-core/`(이벤트 타입은 `src/shared/testbed/testing/sample-core/`)에 있습니다. 공통 시험은 이 위치에서 직접 가져오고 서버 `CORES`에 기대지 않습니다. `testbed-base`는 `CORES`에 샘플 코어를 등록하고, 테스트베드는 `cores/index.ts`의 그 한 줄만 빼고 자기 코어를 넣습니다(`testing/`은 지우거나 고치지 않음).

## 3. 프로세스 구조

```
                ┌──────────────────────── 테스트베드 (Bun 프로세스 = glue) ────────────────────────┐
                │                                                                                 │
  제품 ◀──────▶ │  데이터면: 코어가 연 포트 (TCP / HTTP / MCP / LLM API …)                        │
                │        ▲                                                                        │
                │  Core Host ── in-proc 코어 (기본)                                               │
                │            └─ 외부 코어 (stdio JSON-RPC, 복제 N개) ── Python / Java / …         │
                │            └─ 원격 워커 (WS JSON-RPC, 클라우드 복제) ※ 나중 단계               │
                │        │ emit                                                                   │
                │  Event Bus ──▶ 링버퍼(실시간)  ──▶ Run Store(영속: memory | file)               │
                │        │                                                                        │
                │  Control Service (유일한 원본) ── Control Lease                                 │
                │        ├── REST  /testbed/api/*   ◀── CI, 대시보드의 조작                       │
                │        ├── MCP   /testbed/mcp      ◀── 에이전트                                 │
                │        └── WS    /testbed/ws       ──▶ 대시보드 (스냅샷 + 증분)                 │
                └─────────────────────────────────────────────────────────────────────────────────┘
```

## 4. 원칙

1. **코어는 서버 쪽에만** 둡니다. 브라우저는 보여 주고 명령을 보내기만 합니다.
2. **제어 서비스가 유일한 원본**입니다. REST, MCP, WS는 모두 제어 서비스 함수를 부르는 얇은 어댑터입니다. 같은 동작을 두 번 구현하지 않습니다.
3. **사람 UI와 에이전트 도구의 완전한 동등성은 강제하지 않습니다.** 다만 둘 다 같은 제어 서비스를 부르고, 한쪽에만 있는 기능은 스펙의 "제어 표면" 표에 이유와 함께 적습니다.
4. **모든 일은 이벤트로 남습니다.** 제품의 트래픽, 사람·에이전트의 조작, 코어 상태 변화가 모두 같은 봉투([events.md](events.md))를 씁니다. 대시보드와 에이전트는 같은 이벤트를 봅니다.
5. **데이터면은 제어 락의 영향을 받지 않습니다.** 락은 조작을 막는 것이지 제품의 트래픽을 막지 않습니다.

## 5. 테스트베드 유형

유형은 **코어 단위**로 선언합니다. 한 테스트베드 안에서 여러 유형을 섞을 수 있습니다. 프록시형은 범위 밖입니다.

| 유형       | 방향                    | 예                                                               | 공통 런타임이 주는 것                                     |
| ---------- | ----------------------- | ---------------------------------------------------------------- | --------------------------------------------------------- |
| `passive`  | 제품 → 코어             | TCP echo, MCP 서버 대역, LLM API 대역                            | 데이터면 포트 관리, 요청·응답 이벤트, 결함 주입           |
| `active`   | 코어 → 제품             | 부하 발생기, 주기 호출기                                         | 대상 설정, 속도·동시성 제어, 지연·결과 통계, 복제         |
| `scenario` | 단계 실행 + 기대값 판정 | "로그인 → 토큰 → API 호출 → 차단 확인", 게이트웨이 회귀 시나리오 | 단계 실행기, 단계별 이벤트, 판정(`pass`/`fail`), Run 요약 |

- 시나리오는 직접 호출하는 단계와, 같은 테스트베드 안의 passive 코어가 받아야 할 것에 대한 기대를 함께 담을 수 있습니다. 예: "게이트웨이가 MCP 대역에 `echo`를 정확히 한 번 전달했는가".
- 시나리오 정의 형식은 공통 스키마(JSON/YAML)로 정합니다. 단계 종류(`http.request`, `wait_for`, `check` 등)는 코어가 등록합니다.
- 다른 유형이 필요해지면 `testbed-base`의 결정으로 추가합니다(업그레이드 가이드 동반).

## 6. 확정된 결정

| 주제           | 결정                                                                                                                                            |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 런타임         | Bun                                                                                                                                             |
| 코어 위치      | 서버 쪽만. 브라우저에 엔진을 두지 않음                                                                                                          |
| 레포           | 테스트베드 하나에 레포 하나. 계보와 이력 이어받기는 §2                                                                                          |
| 기본값         | `DB_DRIVER=memory`, `AUTH_DRIVER=none`. 보일러플레이트의 데모 페이지(Todos·채팅)는 `testbed-base`에서 제거                                      |
| 문서 위치      | 공통 규약은 `docs/testbed/`, 테스트베드별 스펙은 `docs/spec.md`                                                                                 |
| 외부 코어      | 다른 언어 SDK, Python 전용 모듈, 대량 연산, Bun으로 낼 수 없는 성능이 필요할 때만. glue가 자식 프로세스로 띄워 감시. docker compose도 허용      |
| 코어 개수      | 한 테스트베드에 코어 여러 개, 같은 코어의 복제도 가능. 보통은 in-proc 코어 하나이며 이때 프로세스를 나누지 않음                                 |
| 이벤트         | 실시간 링버퍼 + Run 단위 영속 저장 + 내보내기                                                                                                   |
| MCP 분리       | 데이터면 MCP(경로는 코어가 정함)와 제어면 MCP(`/testbed/mcp`)를 분리. 제어면 MCP 전송은 Streamable HTTP                                         |
| 제어 락        | 에이전트가 제어 중이면 대시보드 조작을 막고 보기는 허용. TTL 자동 해제. 대시보드 강제 해제 버튼 없음                                            |
| 인증           | 로컬은 없음. 공용 서버·클라우드는 사람 OIDC, 에이전트·CI Bearer 토큰. 브라우저에 토큰을 두지 않음                                               |
| 제품 레포 연결 | 각 테스트베드는 제품 레포에 붙일 `.mcp.json` 조각과 CLAUDE.md 스니펫을 제공 (`docs/agent-usage.md`)                                             |
| 허브           | 여러 테스트베드를 묶는 허브는 만들지 않음                                                                                                       |
| 배포           | 로컬과 공용 서버 둘 다. 제품이 다른 머신에 있을 수 있고, 클라우드에서 여러 인스턴스를 띄울 수 있음                                              |
| CI·레지스트리  | GitHub Actions, 이미지는 GHCR(`ghcr.io/hwahee/<레포 이름>`). 이미지 push는 `main`에서만. 공개 저장소의 이미지는 공개 패키지(pull에 토큰 불필요) |
| 공통 모델      | 매니페스트, 공통 이벤트 봉투, Run, 공통 결함 주입 모델, seed 재현성을 모두 채택                                                                 |

## 7. 공통 환경 변수

env는 **부팅 기본값**만 정합니다. 실행 중 변경은 제어 API로 하고, 재시작하면 사라지지만 Run 메타에 스냅샷으로 남습니다.

| 변수                           | 기본                                   | 설명                                                              |
| ------------------------------ | -------------------------------------- | ----------------------------------------------------------------- |
| `PORT`                         | 포트 블록의 +0 ([ports.md](ports.md))  | 대시보드 + 제어면 HTTP                                            |
| `TESTBED_BIND_HOST`            | 로컬 dev `127.0.0.1`, 이미지 `0.0.0.0` | 데이터면·제어면 바인딩                                            |
| `TESTBED_PUBLIC_URL`           | `http://localhost:${PORT}`             | 매니페스트와 `.mcp.json` 조각에 쓰는 외부 주소                    |
| `TESTBED_EVENT_BUFFER`         | `5000`                                 | 링버퍼 크기(건)                                                   |
| `TESTBED_RUN_STORE`            | `memory`                               | `memory` 또는 `file`                                              |
| `TESTBED_DATA_DIR`             | `./data`                               | file 저장소 위치 (gitignore)                                      |
| `TESTBED_RUN_RETENTION`        | `50`                                   | 보존할 Run 수                                                     |
| `TESTBED_CONTROL_TOKEN`        | (비움)                                 | 설정하면 에이전트·CI 제어면에 Bearer 필요                         |
| `TESTBED_LEASE_TTL_SEC`        | `600`                                  | 제어 락 TTL(초)                                                   |
| `TESTBED_MAX_PAYLOAD_BYTES`    | `16384`                                | 이벤트 payload 상한(bytes)                                        |
| `TESTBED_MCP_MAX_SESSIONS`     | `32`                                   | 동시에 열 수 있는 MCP 세션 수. 넘으면 새 `initialize`가 503       |
| `TESTBED_MCP_SESSION_IDLE_SEC` | `3600`                                 | 이 시간(초) 동안 요청이 없는 MCP 세션은 서버가 닫음(쥔 락도 풀림) |
| `TESTBED_EXAMPLE_CORES`        | (비움)                                 | 함께 등록할 예제 코어(쉼표 목록, 예: `py-echo`). 아래 참고        |
| `<CORE_ID>_*`                  | –                                      | 코어별. 예: `ECHO_PORT`, `LLM_DEFAULT_MODEL`                      |

- 제품이 다른 머신에 있으면 `TESTBED_BIND_HOST=0.0.0.0`과 `TESTBED_PUBLIC_URL`을 함께 바꿉니다.
- `TESTBED_EXAMPLE_CORES`: 예제 코어는 `examples/<예제>/`에 있고, 공통 런타임(`src/server/testbed/examples.ts`)이 목록을 모읍니다. 이름을 넣은 것만 테스트베드의 코어(`cores/index.ts`) 뒤에 등록되며, 모르는 이름이면 부팅이 실패합니다. 기본 이미지와 기본 실행에는 들어가지 않습니다. 지금 있는 예제는 `py-echo`(Python 외부 코어, [external-core-protocol.md](external-core-protocol.md) §10)뿐입니다.

## 8. 배포와 다중 인스턴스

- 테스트베드마다 Docker 이미지를 만듭니다. GitHub Actions는 `check` → `build` → GHCR push 순서이고, push는 `main`에서만 합니다. `testbed-base`가 워크플로 틀을 주고, 각 테스트베드는 이미지 이름만 바꿉니다.
- **독립 인스턴스**: 같은 이미지를 여러 개 띄우고, 각각 자기 대시보드와 Run을 가집니다. 공통 런타임만으로 됩니다.
- **주-워커**: 주 테스트베드 하나에 원격 워커(외부 코어 프로토콜의 WS 전송)가 붙고, 대시보드 하나에서 합산해 봅니다. 첫 클라우드 부하 테스트베드가 생길 때 `testbed-base`에 추가합니다.
